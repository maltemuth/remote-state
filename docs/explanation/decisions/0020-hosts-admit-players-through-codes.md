# 0020. Hosts admit players through single-use codes

Status: Accepted
Date: 2026-09-29

## Context

The library issues and checks tokens, and the implementer decides who may do what ([0015](0015-library-issues-opaque-tokens.md), [0016](0016-authentication-in-library-authorization-by-implementer.md)). Creating and joining a game are where those meet: the host decides who may play, with its own login, which the library doesn't know, and the library has to hand that person a token.

Hooks such as `canCreateGame(user, options)` can't work, since the library has no `user` to pass: the caller has no token yet, and the host's login is opaque to the library. Tokens can't be handed out again either, since they're stored hashed ([0017](0017-hashed-tokens-in-header-and-handshake.md)).

The full flow, with a diagram, is in the [Authorization](../designs/authorization.md#proposal-admitting-players) proposal.

## Decision

- **The host admits people to games.** After its own checks, it calls `admit({ gameId, identity })` on the server object. The identity has an ID of the host's choosing, which the library stores but never interprets, and details for the game, such as a display name.
- **`admit` returns a single-use code,** generated by the library, which expires within a minute.
- **The host returns the code to its client** in the body of its response. Codes and tokens are never put in URLs or passed through redirects.
- **The client exchanges the code for a token** with `POST /api/tokens`, with the code in the body. The response is `{ gameId, playerId, token }`.
- **A player is identified by the game and the identity ID.** When the code is redeemed, the library creates the player if there's none for that identity yet, after the game's rules on joining allow it, through a game hook. Otherwise it returns the existing player.
- **Every redemption issues a new token** ([0019](0019-several-tokens-per-player.md)).
- **The library has no public endpoints for creating or joining games.** `POST /api/games` and `POST /api/games/:gameId/players` are removed. Every app is a host and implements these itself; the example server and the tutorial show how, without any login.

## Alternatives considered

- **Hooks asked by public create and join endpoints,** such as `canCreateGame`. They would need the host's identity, which the library can't provide, or the raw request, which ties hosts to Express and to the order of their middleware.
- **Host middleware in front of the library's routes.** Needs the library to be mounted into the host's app, which isn't possible yet, and still leaves the library to create players without knowing who they are.
- **The host creating players directly and handing out tokens,** through a server-side API. Works, but the host has to keep its own table linking users to players, and a token has to travel to the client, where a code limits what a leak exposes.
- **Host-generated codes.** The library would have to trust their randomness.
- **Keeping public create and join endpoints for standalone use.** Two ways to get a token, and the one used in examples wouldn't be the one real hosts need.

## Consequences

- The host decides who may play in plain code, with its own login; the library never needs to understand it.
- A lost token, a second device or another browser: the host admits the same identity again, and the player gets a new token. No separate reissue mechanism is needed.
- Game logic can receive host details for a player, through the identity.
- Hosts must run `admit` in the same process as the library ([0006](0006-single-process.md)).
- Codes are stored, with their expiry and whether they're used, in a new table.
- Breaking change: clients that create or join games through the library's endpoints must go through their host instead. The example server, its web client, the tutorial and the reference change accordingly.
- Still open ([Authorization](../designs/authorization.md)): how a game is created, what the game's join hook receives, and whether hosts can limit a player's tokens.
